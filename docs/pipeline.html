How the harvest classifier decides

A worker agent finishes a turn and leaves a final message. Most of those messages need nothing from anyone. This pipeline decides which ones do, and it stops at a recommendation.

The order matters

  1. Allow-list. Only sessions you have named may be classified, and a deny entry outranks an allow entry. The list ships empty, so a fresh install classifies nothing.
  2. Trust rule. A status file counts only while it is fresh, measured from the file's own updated_at rather than its mtime, and only while the session has not ended.
  3. Guard. Runs on allow-listed text too, because an allow-listed session can still paste a token or quote a name. It blocks the send, not just the row, and records category names only.
  4. Deterministic checks. Everything a regular expression can settle is settled in code: a commit hash, a line such as 256 passed, a trailing question mark, a permission dialog. Roughly a third of the synthetic fixtures never reach a model.
  5. The model, for the remainder. Six yes/no questions and one choice over five actions, frozen by digest.
  6. Policy. Pure code. A message that claims completion without evidence is never harvested, whatever the model chose.

What it will not do

There is no code path that prompts an agent, keys a terminal pane, or drives a multiplexer, and a test parses the source to prove it. Text inside a message is data: an instruction found there is recorded and otherwise ignored. The output is a row in a log file, and a human reads it.

Part of harvest-classifier. Independent of, and not endorsed by, TypeSafe AI or Anthropic.
